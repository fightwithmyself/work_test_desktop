# 03 提示词剧本(Vibe Coding 逐步执行手册)

> 用法:**按顺序**把每个代码块整段复制给 AI。每一步完成并看到验收证据后,再进入下一步。
> 每个提示词都遵循同一结构:**目标 → 背景与约束 → 验收标准 → 交付证据**。这是让 AI 不"看起来对"而"真的对"的关键。
> 出现问题时不要跳步,用文末的"修复类提示词"。

## 设计原则(面试时可以讲)

1. **一步一个可验收的结果**:每步有明确的"完成"定义,而不是"帮我做完整个项目"。
2. **先测试后推进**:每个模块带自己的测试,测试不过不进下一步。
3. **证据驱动**:要求 AI 贴出命令输出、截图,而不是口头说"已完成"。
4. **决策留痕**:每步要求把决策与你的反馈追加到 `docs/DECISIONS.md`。
5. **文档是 AI 的外部记忆**:换新会话时用"开场提示词"让 AI 重新读文档,避免上下文丢失。

## P2 core 基础:类型、格式化、ffprobe 解析

```
【目标】完成纯逻辑层的第一批模块,全部带单元测试。

## P3 ffmpeg 服务:定位、进程、探测、缩略图

```
【目标】在主进程实现与 ffmpeg 交互的服务层,并用真实 ffmpeg 做集成测试。
【要求】
1. ffmpeg-locator:定位内置 ffmpeg/ffprobe,支持设置里的自定义路径;处理打包后 app.asar 到 app.asar.unpacked 的路径替换(见风险 R-04)。
2. process-runner:封装 spawn(只用数组参数,禁止 shell:true),提供按行读取 stdout/stderr、超时、取消、Windows 下用 taskkill /T /F 杀进程树。
3. probe-service:调用 ffprobe,返回 VideoInfo 或结构化错误(文件不存在、不是视频、文件损坏分别区分)。
4. thumbnail-service:默认取时长 10% 处一帧,-ss 放在 -i 前,缩放到 320 宽,返回 JPEG data URL;极短视频取第 0 帧;无视频流时返回占位。
5. scripts/make-fixtures.ts:用 ffmpeg lavfi 生成测试视频(含:正常、无音轨、竖屏、极短、路径含中文和空格),输出到 tests/fixtures/generated(已在 .gitignore)。
【验收】npm run test:integration 通过;测试包含"路径含中文和空格"、"损坏文件(写入随机字节)"、"不存在的文件"、"取消正在运行的进程后无残留 ffmpeg 进程"。
【交付】贴出测试输出;追加决策;提交。
```

```

## P6 转换器与任务队列

```
【目标】实现转换执行与队列,并用真实 ffmpeg 做集成测试。
【要求】
1. converter:单任务生命周期——写入同目录临时文件 → 成功后原子改名 → 失败或取消则删除临时文件。取消流程:先向 ffmpeg stdin 写 q,约 1.5 秒未退出则 taskkill /T /F。

```

- AMF:"DLL amfrt64.dll failed to open"

3. error-translator:把 ffmpeg stderr 翻译成"问题 + 建议"。至少覆盖:上面两条真实报错、磁盘空间不足、权限不足、输出文件被占用、编码器不支持、文件损坏、找不到流。
【验收】单元测试用上述真实报错断言翻译结果;集成测试验证回退逻辑(可用一个必定失败的编码器名模拟)。

## 通用修复类提示词

**A. 报告一个 bug**
```
我发现一个问题:【现象】。复现步骤:【1... 2... 3...】。期望:【...】。
请先不要改代码:1) 复现它并贴出证据;2) 定位根因(指出文件和行);3) 先写一个能让这个 bug 失败的测试;4) 再修复并确认测试通过;5) 跑一遍全部测试确认没有回归;6) 把根因追加到 docs/DECISIONS.md 的"缺陷记录"。
```

**B. AI 说"完成"但我不信**
```
你刚才说完成了,请提供证据:1) 这次实际运行的命令及原始输出;2) 对应功能的截图或运行现象;3) 哪些路径你没有测过。不要用"应该可以"这类措辞。
```

**C. 卡住时做根因分析**
```
同一个问题已经试了两次没解决。请停止尝试性修改,先做根因分析:列出至少 3 个假设,每个假设给出一个能快速证伪的最小实验,执行实验后再决定怎么修。
```

**D. 我要改变一个决策**
```
我想改变 D-【编号】:【原决策】改为【新决策】,原因是【...】。
请评估影响范围(哪些文件、测试、文档要改),给出风险,等我确认后再动手,并在 DECISIONS.md 里标注旧决策被新决策取代。
```

**E. 每一步结束后的收尾检查**
```
请做本步骤收尾:1) 运行 typecheck、lint、全部测试并贴结果;2) 检查 git status 没有不该提交的文件;3) 把本步骤的决策与我的反馈追加到 DECISIONS.md;4) 提交;5) 用 3 句话告诉我下一步该做什么、有什么风险。
```

**F. 面试前复盘**
```
请基于 git 历史、DECISIONS.md 和 TEST_REPORT.md,帮我准备面试讲稿:1) 3 分钟项目介绍;2) 5 个体现 AI 工程能力的关键决策(每个说清备选方案与取舍);3) 3 个 AI 犯过的错以及我是怎么发现并纠正的;4) 面试官可能追问的 8 个问题及回答要点。
```

---

## 给你的使用建议

1. **一次只发一个步骤。** 等 AI 贴出验收证据,你亲自看一眼(运行一下界面)再发下一个。
2. **你的意见比提示词更重要。** 看到界面觉得别扭,直接说"这里我觉得…",AI 会记入决策文档,这正是面试官想看的"开发者的决策选择与反馈"。
3. **换会话必先发 P0。**
4. **不要跳过 P10 和 P11。** 题目最后一条强调"自己都不测试不行",这两步就是证据。
5. **遇到 AI 反复出错,用修复类 C**,让它先做根因分析,不要让它反复试错。
